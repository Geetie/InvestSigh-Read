## 一、致命问题（方案必须修正才能过）

### D1. 「题→篮子列→格」是系统明文禁止的做法，且收束工序按提案自己的定义根本读不到分册 —— 归格只能靠猜

**问题**：提案的全部落点都压在「归格是规则（机械映射、不判断）」上（§5:78、§3 F4、§8:129）。实读后这条前提整体不成立：系统反复明令「篮子 ≠ 格」，分册「落哪个篮子」列给的是**裸代号＋括号篮子名**，且一题多格、三题是判断指令；更致命的是 §4 C 与 §6 把收束输入限定为「只读已入库卡＋三本账＋节点→格映射表」，**分册问句表不在只读清单里**——归格所需的唯一映射源被排除在外。

**证据**：
- 明文禁令：`01-监管一手披露.md:17`「**落点 = 估值模型上的格**；**篮子只是存放答案的地方**；**"为填格而找信息" = 判失败**」；`03-卖方与共识.md:24`「篮子｜存放答案的容器（篮子清单），**一格可以对应多个篮子；篮子不是格**｜以为填了篮子就等于填了格，最后模型还是空的」；`03-卖方与共识.md:66` 同义重申；`建模_v1.md:152`「落点＝估值模型上的格，篮子只是存放答案的地方（**两个东西，不许焊成一个词**）」。提案 §3 F4「题→格的映射是现成的」正是把这两个词焊成一个。
- 「八行映射表」被误引：`01-监管一手披露.md:20-29` 右列是**人话影响**（「规模在不在长、口径可不可比」「变现率靠"看的人更多"还是"每人更值钱"」），既无格名也无格 ID，不是题→格映射表。
- 分册真实形态（`01-型/8-K与EX-99.1.md:141-153`，列名逐字为「落哪个篮子」）：Q1 = `M-2 变现率（季度序列趋势底座）`——**M-x 裸代号＋括号篮子名**，与提案 §5 硬约束 1「禁裸代号、键＝格名＋口径」直接相撞，需要一层提案没提供的 M-2→「变现率」翻译；Q3 = `M-2 变现率 · M-7 资本开支`、Q7 = `M-9 拖累项 · M-5 成本·折旧`——**一题多格，不是函数映射**；Q9 =「按事实填哪一格；**挂不上 ⇒ 报缺格**」、Q10 =「守门（内控与审计事项）」、Q11 =「兜底（增量信息）」——**三条是判断指令/非格值**，不是机械规则。`01-型/10-K.md:141` 自承「最后一列给的就是落点…括号里是篮子」，术语本身即混用。
- 收束读不到分册：§4 C（:59）、§6（:91）「只读已入库卡＋三本账＋节点→格映射表」；§5 输入 2（:69）却写「分册问句表的落哪个篮子列 → 题→格映射」——**同一份提案两处自相矛盾**。`server/apply-proposals.mjs:4` 还明令「只改读法列（题干/需件/频次/**篮子列**不动）」，34 分册各自维护，全库没有集中的题→格表。
- 实卡三张无落点信息：02 `-pilot` 卡 `:81,135,148,177` 仅 4/13 题有「喂变现格（**M-2**）」的**散文裸代号句**（且是 agent 的判断，非字段）；03 AMD 卡（Q1–Q12）与 01 8-K 卡**零格信息、零篮子字段、零结构化增量标记**；01 卡 `:75` 明写「几乎没有一项能塞进现有格」，却没有任何「归格失败」结构化标记可供收束提取（提案 §8:129 却要求留痕）。三卡 frontmatter 均无篮子/格/proxy_tier 字段。
- 题号异质：02 `-pilot` 用 `## 1 ·`（无 Q 前缀），01/03 用 `## Q3 ·` 且**跳号**（01 卡从 Q3 起，Q1/Q2 被「采不到整节删掉」删掉）——「按题号切分」没有统一规则。

**建议修法**：① 先建一张**集中、版本化、单点真源**的「(分册, Q号) → 格名＋口径」映射表，显式写明「篮子≠格」、一题多格的拆分规则、Q9/Q10/Q11 三条的例外处理，并列入收束的显式只读输入（同步删掉 §4/§6「只读三样」的措辞）；② 承认「从散文里抽格 = 语义判断」，删掉「归格不判断」的宣传，或在卡面加结构化题号/格锚（那就要改卡格式，与「卡格式零变化」二选一并明说代价）；③ 试点第一项不是跑收束，而是**先量覆盖率**：现有三张实卡 1/3 有零散痕迹、其余 0，这个数现在就能测。

### D2. C 方案没有运行位置：唯一能挂的「主控侧加工步骤」全库不存在，且被契约明文永禁

**问题**：§4:61「收束挂在**现有主控侧加工步骤之后**（例如卡入库／`research_ingest` 编译完成后由主控执行），**不新增 automation**」。实读：这两个例子都不构成可挂载的钩子；「不新增 automation」与「每批多一次收束」在物理上不可兼得。

### D3. 「补上既有但空转的对外通道」是偷换概念：七件契约整体从未落盘，且两套写入契约互相打架

**问题**：§3 F2/F3/F6 与 §4:49 的论证是「`变更提案.md` 是体系既有的对外裁决通道，只是从没被生产出来，补上即可」，因此「批内契约一个字不动」＋另建主控侧 `_ledger-proposals.md`。实读：不是一条通道空转，是**整套七件契约与实跑链路脱节**；提案补的也不是那份 `变更提案.md`，而是另一套东西。

**证据**：

- 第三套同名机制被漏掉：`server/apply-proposals.mjs:2-4`「**逐题提案落库**——把提案文件里的『读法列修改后全文』写进分册问句表读法列；真源纪律：只改读法列（题干/需件/频次/**篮子列**不动）」，消费 `corpus/prompts/提案/02-业绩与沟通-逐题提案.md` 与 `03-卖方与共识-逐题提案.md`。提案全文**一次都没提它**，三套「提案」概念（估值格变更提案／逐题读法提案／主控提案账）混用。

### D4. 5 个末端探测器实质为空：CRED 参数在实卡里不存在，且 3 个末端不在自己引用的映射表覆盖内

**问题**：§2:33「只消费上游已经产出的卡的答案」＋ §5:75「CRED 按 proxy_tier 下调确信度」＋ §5:71 引用「节点→格映射表（7 行）」。实读：参数拿不到、末端不在表内、判断已被批 agent 做完 —— 接入后产出只能是二次复述。

**证据**：
- `proxy_tier` 等是**建模文档的设计字段**：`建模_v1.md:59-60`「字段…内嵌参数：disclosure_status / proxy_tier / confidence_cap / cycle_position」「**全局字段层**（每节点登记时必填…）」——它是探测器登记表的列，不是卡字段。三张实卡 frontmatter＋正文**零出现**；`server/` 无任何注入；收束只读「卡＋三本账＋映射表」⇒ **拿不到 proxy_tier**。「按 proxy_tier 下调确信度」只能新造一个从依据区散文推断 tier 的判断——那既不是「规则」，也没有可回溯来源（违反 §5 硬约束 2）。
- 映射表不覆盖末端：`建模_v1.md:154-163` 的 7 行是 **E1、F1、F2、F3、F4、E2、D6**——**没有 E3、没有 CRED、没有 T1**；`:164` 硬约束「新增格走变更提案建格；**映射表未覆盖的节点输出不得生成提案（防提案键污染）**」。按提案自己引用的规则，它接的 5 个末端里有 3 个（E3 资本配置腿 / CRED / T1 收束）**不得生成提案**；而 §5:76 恰恰让 T1「合并成一行提案」、E3「判断配置格」。同时表里 5 行（F1–F4、D6）属于提案声明「不接的上游 31 节点」，接不上。E3 在建模文档里唯一近似行是 `F4 现金桥 → 资本配置格`（:160），那是上游节点，不是 E3。
- 判断已被批 agent 做完：`01-8-K.../material.md:125-131`（Q10 逐条分辨 filed vs furnished、给出「引用措辞分两级」——这正是 CRED 的实质）、`:75`「几乎没有一项能塞进现有格」、`02-...-pilot/material.md:131-135`（指引兑现风格按收入/费用/资本开支三端拆开、并写「作为变现格与资本开支格判断的置信修正使用」）、`:143-147`（假设账 A-01~A-07 到期核对、两账矛盾处理）。信源分层、增量、基线对照、归格判断全在卡里。末端探测器「只读答案再判断要不要提案」**新增信息为零**。
- 跨批对照基础稀疏：三本账标题全部是「· META」（`_ledger-guidance.md:1` 等），只覆盖单一标的；`_ledger-assumptions.md:23`「首版仅覆盖 2 份卡…其余待逐卡回填」、`_ledger-tone.md:41`「首版两主题…其余待逐卡回填」、`_ledger-guidance.md:16-22`「已知缺口与下一步」；`server/kit.mjs:110` 账本映射表只有 `{指引账, 我方假设账, 骨架}` —— **措辞账不在投喂映射内**，且 `_skeleton.md` 全库不存在；路径写死 `output/<ticker>/_ledger-*`（:111），非 META 标的直接 gaps「（未建）」。§5「三本账的当季相关行」没有定义"当季"的选取规则（措辞账按主题分段、不按季）。

**建议修法**：① 补齐映射表的 E3/CRED/T1 行，或明说末端输出**不生成格提案**、只做核对留痕（那要重写 §2/§5 的探测器职责）；② 若要 CRED，必须先把 `proxy_tier` 等落到卡的结构化字段——那必然改卡格式，与「卡格式零变化」二选一；③ 给「新增信息」一个可证伪判据（例：提案行的依据必须指向**账本中卡面没有的行**），否则试点没法证明没退化成复述。

### D5. 幂等规则自相矛盾，「零提案报警」在自家纪律下永不触发

**问题**：§6:99「同『卡 id＋格名』**只追加一次**状态变化（新提案／复核不改／撤销），重跑不改旧行」＋ §5:76 / F2「**『核过了、不用改』也要写**」＋ §6:100、§8:130「**连续多批零提案行 = 软观察报警**、零行本身就是异常」。三条纪律互相抵消。

**证据**：
- 若每批都必须写「核过了不用改」行 ⇒ 每批都有行 ⇒ ① 同键多行，「只追加一次」被击穿；② 「连续零提案行」**永不成立**，空转报警永不触发。提案把「报警条件」和「必须产出」写成了同一份文件的两种状态，没区分提案行与 heartbeat 行。
- 键三处定义不一致（§5:81「格名＋口径」、§6:99「卡 id＋格名」、`RUN-PARALLEL.md:27`「格名＋口径」），且都不含「腿」与「口径」，E1/E2 同时命中一格时无法消歧。
- 三本账纪律是「行只追加不改写」（`_ledger-guidance.md:4`、`_ledger-assumptions.md:4`），提案 §6:91 沿用「同四纪律」。但「状态＝新提案/复核不改/撤销」需要**改写或事件重放**才能得出「当前状态」；追加式 md 没有当前态概念，提案没定义消费者如何取最新态，也没定义「撤销」如何生效。

**建议修法**：把账定义成 event log：每行带 `事件id（内容哈希）/卡id/格名/口径/腿/事件类型/时间`，幂等键＝事件 id；「当前状态」由重放得出并写成显式规则。「核过了、不用改」改成**每批一次的批次级 heartbeat 行**（与提案行不同标记/不同节），空转报警改为「缺 heartbeat」而不是「零提案行」。统一键定义，把「口径」「腿」纳入键。

### D6. 「可读性零影响」＝「收益零」：产出是一份没有任何消费端的机器账，对主目标无贡献

**问题**：§7:113「不进卡面；老板读到的卡与现在完全一样」、§7:116「估值模型＝零（只提案不改模型）」、§7:115「入库由主控侧追加」。全链路找下来，这份 `_ledger-proposals.md` **没有任何消费者**：对「帮老板读得更快」的主目标贡献为 0，却要每批多一次收束判断（§7:119）＋多一本账的维护。

**证据**：
- 裁决通道不指向它：`写法规范.md:225` 终审走 `变更提案.md` 五列机制。
- 估值模型不改（§7:116、§5 硬约束 4），卡面不变（§7:113），批 agent 不读（§7:112），公共网不接（§7:118）。
- 机器侧不消费：`check.mjs` 全文只校验 `material.md` 与 `output/<tk>/_ledger-*` 的**算术自洽**（:218-239），不读提案内容；`server/pack-ten.mjs:134,147,171` 只打包 `_ledger-guidance.md` 作投喂；`server/` 全库 Grep「proposals/提案账」只命中 `apply-proposals.mjs`（处理的是**读法列提案**，D3）与 `prompts.json:689` 的展示标签。`public/` 全树检索 `_ledger` 只命中 `public/data/network/detectors.json:257` 的一句 forage 描述（`_ledger-macro`），**没有任何账本/提案展示页**。
- §7:114 说要给 `check.mjs`「＋1 项软观察：校验提案账」——那是**让校验器去读账**，不是让老板或裁决流程消费结论；且这项改动本身会改 `server/check.mjs` 真源（见重要问题 I1）。

**建议修法**：先回答「谁会在什么决策里打开这本账」并指名消费动作（终审指针改指、纳入报告⑥变更提案指针、或给 `#/network` 加一个落地视图）。若答案仍是「只有主控自己写、自己看」，应把方案定位从「接入阅读器流程」降为「内部核对台账」，并据此重算成本收益（见 I3）；否则「零影响」这个卖点恰恰证明它没接进任何流程。

## 二、重要问题

**I1. `check.mjs ＋1 项软观察`＝改 server 真源，却被「零改动／不动真源」清单漏列，且新账会落进现有账本算术守卫的扫描面。** §7:114 要 check 校验「格名是否属既有枚举、依据能否回溯到卡」——这必须改 `server/check.mjs` 源码；但 §6 标题「不动任何真源」、§6:103 零改动清单（白名单/kit/模板注释块/34 分册读法列/写法规范/卡格式）**没有 check.mjs**，§8 验收⑤⑥也没覆盖「check diff 为零」。另外 `check.mjs:220-223` 遍历 `output/` 下每个目录（含 `meta`）里的 `_ledger-*` 文件，新增的 `output/meta/_ledger-proposals.md` 会被扫到；`:226-236` 对 `^\|\s*\d{4}Q` 开头且 cells[2] 含 `$x-y billion`、cells[3] 含 `x 亿美元` 的行做算术判定并计入 `ledgerBad` → `:246-248` 硬失败 `exit(1)`。若提案账某行写成 `2026Q4 | …` 且「现在/改成」列恰好带 `$…billion` 与 `…亿美元`，会**误伤批 agent 定稿判门**。修法：把 `check.mjs` 明确列入改动清单并写入验收；新账要么放不被该守卫扫描的目录，要么在守卫里加前缀白名单。

**I2. 试点验收 7 项里至少 5 项不可执行或无法证伪。** §8:133 逐条核：①「格名合法」——全库**没有集中的格枚举表**，格名散在 34 分册，且含「守门」「兜底」「按事实填哪一格」等非格值，机器判不了合法；③「确信度有参数来源」——`proxy_tier` 等参数不存在（D4），无法验；⑤「卡面 diff 为零」——可用 git diff，但试点卡 `-pilot` 是 **2026-04-30 的历史旧卡**（`output/meta/02-...-pilot/material.md:7`），不是 §5:68 说的「本批新入库卡」，它根本不会触发 C 方案的「卡入库」事件 ⇒ **试点没验证触发点**；⑥「批 agent 提示词 diff 为零」——没有定义"提示词"文件集合（分册？RUN-PARALLEL？写法规范？kit？），也没有改前基线：唯一近似的 `批次环境.json`「手册 sha256」（`RUN-PARALLEL.md:29`）**本身从未落盘**（七件零结果），且 §8 只「跑一次收束」，无前后两批可比；⑦「提案账可去重重跑」——与 D5 冲突，规则不成立。②「依据可回溯到 p.N」是 7 项里唯一现成可执行的（实卡依据区确为 `- p.N｜…`）。另「03 类一批」无可指认对象：`runs/` 无批次目录，`output/` 按标的/材料组织，只有 `pipelines/_runs/<日期>/01..07.json`（**采集 run**，不是阅读批）。修法：先补枚举表、基线快照与批次定义，再把验收重写成可机器判定项；试点必须包含一张**当批新入库**的卡。

**I3. 成本收益不成立，存在明显更轻的做法。** 成本：每批一次 LLM 收束判断（§7:119）＋一本新账＋check 改动＋34 分册映射维护；收益：一份无人消费的账（D6）。更轻做法：把「节点→格映射表」做成 `check.mjs` 的**一条静态校验**（格名属枚举、依据 `p.N` 可回溯到卡、禁节点名做提案键、禁裸代号），**不跑 5 个探测器、不建账、不新增文件、不新增 automation**——`check.mjs` 是全库唯一真正在跑的机器钩子（`:3` 自述＋`RUN-PARALLEL.md:25`「定稿前判门」＋实卡全在 `output/` 且被它校验），挂载点现成、误报可测。修法：先上这条静态校验，跑两批看误报率与覆盖率，再决定要不要上「收束判断＋提案账」；把省下的判断成本写进 §7 成本栏做对比。

**I4. 文档版本与引用口径混乱，执行者会拿错真源。** §5:71 说「`节点→格映射表`（**v2 文档** §四·补2，7 行）」、§1 说「通用探测器网络 **v2** 用户已通过」，但仓库里只有 `docs/通用探测器网络_建模_v1.md`（标题「建模 **v1**」），v2 只是文内「三·补 · v2 节点变更」一节（:126-131）；「7 行」属实但内容覆盖的是上游节点（D4）。§3 F4 引用的「01 主件 §一 八行映射表」实为定性定位表（D1）。修法：统一文件名/版本号，逐条核对引用是否指向真实存在的内容，把「映射表 7 行」的实际覆盖范围写进提案。

**I5. 卡格式异质性被试点范围掩盖。** `## 1 ·`（02 `-pilot`，无 Q 前缀）vs `## Q3 ·`（01/03，且跳号）；frontmatter 有的带注释块（03 AMD 卡 `:2-16`）、有的不带；`material.md` 不在七件清单里（D3）。§5「按题号切分」需要兼容规则，而试点只用 `-pilot` 这张特殊卡会掩盖它。修法：试点必须含至少一张标准 01 与一张标准 03 卡，并把题号归一化规则写进运行契约。

**I6. 账本不是「可被收束工序直接读」的结构化数据。** 三本账列数各异（指引账 6 列、假设账 8 列、措辞账 3 段各 4 列）、单元格是中文长句（如「收入高于上限；全年费用落区间内；全年资本开支高于上限」）、都带「已知缺口与下一步」叙述节与「重算于/登记于」列；`_ledger-tone.md:42` 维护触发写的是「每季电话会卡入库时追加行」——**是纪律不是钩子**。`check.mjs:228-231` 只能靠正则硬解析 `$x-y billion` ＋ `x 亿美元` 一种模式，佐证机器可读性很差。§5「三本账的当季相关行」缺行级选取规则。修法：要么接受「读账＝LLM 判断」并计入成本，要么先给三账补一层机器可读的摘要/索引（那是新增真源）。

**I7. `output/meta/` 目录语义混用。** 它同时是「META 标的的实卡目录」（数十张 `output/meta/<材料id>/material.md`）与「主控账本目录」（`_ledger-*.md`）；`store.mjs:86` 的 `listMaterialFiles()` 只认两级子目录，而 `check.mjs:220-223` 把 `meta` 当 ticker 扫 `_ledger-*`。新账夹在中间，容易被两类扫描器交叉误判。修法：给主控侧账本单独目录（或至少在文件前缀/守卫里显式区分），别继续往 `meta/` 堆。

## 三、可接受的风险

- **网络本体不进提示词/卡面**（§1:17、§9）：站得住。`RUN-PARALLEL.md:9,15,21-31`（一批一跑、白名单 7 件、多一件守卫报错）与 `01-监管一手披露.md:4`（可写边界）确实容不下 36 节点整套搬入；「整套搬入不可能」的前提判断正确。
- **「只提案、永不改估值模型」**（§5:84、§7:116）：与 `RUN-PARALLEL.md:15` 模式 A 铁律一致，不引入模型侧风险。
- **撤回原待批第 3 项**（白名单 7→8 ＋ `_ledger-macro`，§5:85、§9、§附:161）：避免了一次真源大改；`建模_v1.md:147` 自己也标「契约变更待批（真源变更不擅动）」，撤回方向正确。
- **「依据写 卡 id／题号／p.N，回溯不到作废」**（§5:82）：与 `check.mjs` 的 R1/R2 依据校验、实卡 `- p.N｜逐字原文` 登记格式同向，可实现；也是本次验收里唯一现成可执行的一项。
- **「归格失败留痕、不静默丢」「空转要可见」「先试点后铺开」「批准前不动真源」**（§8:129-131、§10:151）：运维意识与流程纪律正确，只是与「零行报警」和追加式幂等打架（D5），修掉即可保留。

## 四、攻击后确认站得住的部分

- **事实核查属实的四条**：F1（实卡目录只有 `material.md` 一个文件）、F3（全库 `find` 无任何 `变更提案.md`）、F5（`check.mjs` 只判 `material.md` 单卡门，不校验七件产物）、F6（`写法规范.md:225`「冲突走 `变更提案.md` 五列机制，本文件终审」）—— 这是提案里少数经得起逐字实读的证据，可惜被用来支撑了一个错误的推论（D3）。
- **「末端 5 个不进批 agent 提示词、不改卡面」作为约束**：正确。`RUN-PARALLEL.md:19`（不给读者看的不写）、`:21`（7 件名字逐字固定）、`01-监管一手披露.md:4`（可写仅 output/<标的>/<材料id>/）都支持；问题不在约束，在约束之后方案没剩下输入、运行位置和消费者。
- **沿用既有硬约束的方向**：「禁裸代号、禁节点名做提案键、键＝格名＋口径、依据可回溯」出自 `建模_v1.md:152,164` 与 `RUN-PARALLEL.md:27`，方向对（但提案自己又冒出「卡 id＋格名」，见 D5）。
- **「归格是规则／要不要提案是判断」这条分工意图**：作为防退化的设计意图是好的，可惜前半句在现有系统里不成立（D1）；把「归格」也如实标成判断、并给它一张映射表真源后，这条分工仍可救。
- **提案的自我边界意识**：§8 主动列了「卡面没有结构化增量标记」「提案账空转」「契约重名」三条风险，§9 明确不做清单，§10 写「批准前不动任何真源」——红队没在这些地方找到隐瞒；问题全部出在**证据误引与架构前提**，不在态度。

---

> 结论：**不建议按现稿批准**。六条致命问题里，D1（输入断）、D2（无运行位置）、D6（无消费者）三者叠加，意味着方案既拿不到落点、又没有地方跑、跑完也没人用；D3/D4/D5 则是契约、实质与幂等层面的硬伤。最小可批路径：先把 I3 的静态校验落地（复用 `check.mjs` 这一唯一在跑的钩子），同时补 D1 的集中映射表真源与 D2 的运行契约，再重新提交。
