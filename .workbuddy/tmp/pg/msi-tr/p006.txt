这均衡了专家训练的负载，并提升了分布式硬件上的 MFU。超大规模云厂商的网络正是为这种并行方式量身打造的，我们在网络模型（Networking model）中对此有详尽的覆盖。
这种做法的缺点则与 token 选择架构相反。专家选择路由可能导致某些“受欢迎”的 token 被多个专家同时处理。虽然这不会造成 token 选择路由中那种训练瓶颈，却可能导致模型泛化能力下降，因为此时LLM 不再对所有 token 一视同仁。此外，大多数 EC（expert choice，专家选择）模型都需要用 TC（token choice，token 选择）训练来收尾，才能得到一个有效的 LLM。
推理也是 EC 的另一个问题。推理分为两步：prefill 与 decode。在 prefill 阶段，用户的提示词被编码并载入 KV cache（键值缓存），这一步受算力（Flop）约束。在 decode 阶段，模型逐个 token、逐层地计算注意力并跑完前馈网络。
在这里，专家选择路由就力不从心了，因为最初每一层每个专家只能从 1 token × batch size 这么多token 中挑选，导致相比训练时，每个专家拿到的 token 集合非常之小（一次训练示例可能是 8k 序列长度 × 16 batch size = 每次 128k 个 token）。而像训练时那样能看到整个序列，又会破坏现代自回归模型的因果性，因此即便是 EC 模型也要混用 EC 与 TC。
Meta 在训练中途从专家选择切换到了 token 选择路由，这对 EC 模型而言并不罕见。然而，这次切换带来的性能下滑，最终使得模型明显逊色于一个全程用 TC 训练出来的模型。
数据质量：自伤之痛
Llama 3 405B 用 15T token 训练而成，我们认为 Llama 4 Behemoth 需要的 token 数量要多得多，量级大出 3—4 倍。获取足够高质量的数据是一大瓶颈，西方超大规模云厂商无法靠抄袭其他模型输出这份“作业”来抄近路。
在 Llama 4 Behemoth 之前，Meta 一直使用公开数据（如 Common Crawl），但在训练中途切换到了自建的内部网络爬虫。这种做法总体上更优，却也适得其反。团队在清洗和去重这条新数据流时举步维艰，相关流程从未在大规模场景下经受过压力测试。
此外，与包括 OpenAI 和 DeepSeek 在内的所有其他领先 AI 实验室不同，Meta 并不使用 YouTube 数据。YouTube 的讲座字幕及其他视频是极其宝贵的数据来源，缺少这类数据，该公司在打造多模态模型时可能会力不从心。
